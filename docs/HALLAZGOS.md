# Hallazgos (diagnóstico del software inicial)

> **Nota sobre las rutas (LB-4, RFC-004):** las ubicaciones de los hallazgos H-001 a H-032 corresponden a la estructura de carpetas **anterior a LB-4** (`proyecto_valdiviezo/`, `backend/backend/`, `tests/`, `BDPostaMedica.sql` en la raíz) y no se reescriben, porque registran dónde estaba el problema cuando se detectó. Para ubicar cada archivo en la estructura actual, ver la tabla "ruta anterior → ruta nueva" de `docs/rfc/RFC-004.md`. Los hallazgos desde H-033 usan las rutas nuevas.

Diagnóstico de la línea base LB-0. Los IDs (H-001, H-002, …) son permanentes: se citan en las solicitudes de cambio (RFC) y no se renumeran.

**Gravedad:** Crítica / Alta / Media / Baja.

**Tipo de mantenimiento** (clasificación del curso):
- **Correctivo:** corrige un error que ya ocurre.
- **Preventivo:** no hay falla, pero mejora la mantenibilidad (duplicación, mala estructura, falta de principios SOLID).
- **Adaptativo:** adapta el sistema a un cambio del entorno.
- **Perfectivo:** agrega o mejora una funcionalidad.

**Cambio que lo atiende:** el cambio planificado que resolverá el hallazgo (RFC, reorganización o refactorización R1–R4). "Pendiente" significa que todavía no hay un cambio asignado.

> **Las refactorizaciones no corrigen hallazgos correctivos.** Una refactorización (R1–R4) y la reorganización de carpetas no cambian el comportamiento externo. Por eso los hallazgos correctivos que no tienen un RFC asignado (por ejemplo H-012, la doble reserva) **deben seguir fallando igual que en LB-0** después de cada refactorización. Si una prueba de un hallazgo correctivo cambia de resultado tras una refactorización, la refactorización alteró el comportamiento y eso es un error.
