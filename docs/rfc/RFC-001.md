## Descripción del cambio

### Motivación (qué pasa hoy)
- **H-001 — Acceso con cualquier DNI.** El login de paciente tiene un atajo de pruebas: si el backend responde con error y la clave es `123456`, guarda una sesión falsa del paciente 1 y deja entrar. En **P10**, el DNI inexistente `99999999` con clave `123456` recibe `401` del backend y aun así entra a `/welcome` con `userName = "Juan Perez (Mock)"`. Lo mismo pasa con el backend apagado.
- **H-002 — Sesión inconsistente y cierre de sesión que no cierra.** Cada rol guarda claves distintas en localStorage: paciente y médico usan `userId`, `userName`, `userType`; admin usa `userTipo`, `userNombre`, `userApellidos`, `userDni`, `userRol`. Cada rol cierra sesión de forma distinta. En **P17**, tras "Cerrar Sesión" como paciente, el localStorage queda intacto y `/paciente/mis-citas` sigue mostrando las citas: otra persona en el mismo equipo accede a los datos del paciente.
- **H-003 — Mensajes de error distintos.** Ante credenciales inválidas, paciente y médico muestran "Credenciales inválidas" y admin muestra "Error al iniciar sesión. Por favor intente nuevamente." (**P08**). Ningún rol distingue entre credenciales inválidas y servidor caído.

### Propósito (qué debe pasar después)
1. Si el login falla por cualquier razón (401, backend apagado, error de red), no se guarda nada en localStorage y no se entra al sistema. Se elimina el atajo de la clave `123456`.
2. Los 3 roles guardan la sesión con el mismo esquema de claves: `userId`, `userName`, `userType`. No queda código en uso que lea una clave que ya no se escribe.
3. "Cerrar Sesión" borra la sesión completa en los 3 roles, incluido el paciente.
4. El mismo caso muestra el mismo mensaje en los 3 roles:
   - credenciales inválidas (HTTP 401): "Credenciales inválidas"
   - backend sin respuesta: "No se pudo conectar con el servidor. Intente nuevamente."

## Análisis de impacto

### Técnico — archivos que se modifican
Todos en `proyecto_valdiviezo/src/app/`. No se modifica el backend ni la base de datos.

| Archivo | Cambio | Hallazgo |
|---|---|---|
| `login-paciente/login-paciente.component.ts` | Quitar el atajo de la clave `123456`; mensajes de error 401 / sin conexión | H-001, H-003 |
| `login-medico/login-medico.component.ts` | Guardar la sesión solo si el usuario es médico (hoy guarda antes de comprobar el rol); mensajes de error | H-001, H-003 |
| `login-admin/login-admin.component.ts` | Guardar `userId`, `userName`, `userType` en lugar de las 6 claves propias; mensajes de error | H-002, H-003 |
| `admin/dashboard/admin-dashboard.component.ts` | Cerrar sesión con `AuthService.logout()` (borra todo) en lugar de borrar 6 claves sueltas | H-002 |
| `welcome/welcome.component.ts` y `welcome/welcome.component.html` | "Cerrar Sesión" del paciente pasa de enlace a botón que llama a `AuthService.logout()` | H-002 |

El médico ya cierra sesión con `AuthService.logout()` (`localStorage.clear()`): no se modifica.

**Lecturas de claves viejas (búsqueda con grep):** en el código en uso, las pantallas solo leen `userId` (`paciente/mis-citas`, `paciente/historial-medico`, `paciente/registrar-cita`), que se mantiene. Las claves de admin (`userTipo`, `userNombre`, `userApellidos`, `userDni`, `userRol`) solo se escriben y se borran; nadie las lee. `token` y `role` solo aparecen en componentes huérfanos que no están en las rutas (H-009 y H-027): quedan fuera del alcance.

**Restricción:** los 3 componentes de login se corrigen por separado, cada uno en su archivo. Unificarlos es la refactorización R1 DRY, que se hará después.

## Plan de back-out
Si el cambio falla, se descartan los cambios y se vuelve al estado de LB-0:

- Antes del commit (cambios sin confirmar):
  ```
  git restore --source=LB-0 -- proyecto_valdiviezo/src/app
  ```
- Después del commit de LB-1 (se crea un commit que deshace el cambio, sin reescribir la historia):
  ```
  git revert --no-edit LB-0..LB-1
  ```
  Si se prefiere revertir solo el commit del RFC: `git revert --no-edit <hash del commit RFC-001>`.

Luego reiniciar el frontend (`npm start`) y correr la batería para confirmar que los resultados vuelven a ser los de LB-0.

## Evaluación post-implementación

### ¿Se cumplieron los objetivos?
Sí. Los cuatro objetivos se verificaron con la batería de pruebas (`docs/PRUEBAS.md`, sección "Resultados de LB-1"):

| Objetivo | Prueba | LB-0 | LB-1 |
|---|---|---|---|
| Si el login falla no se guarda nada y no se entra (H-001) | P10 (DNI inexistente + `123456`) | Entraba como "Juan Perez (Mock)" | `401`, se queda en `/login-paciente`, localStorage `{}` |
| | P18 (backend apagado + `123456`) | (habría entrado por el atajo) | `ERR_CONNECTION_REFUSED`, no entra, localStorage `{}` |
| Un solo esquema de sesión (H-002) | P05, P06, P07 | Admin con 6 claves propias | Los 3 roles: `userId`, `userName`, `userType` |
| Cerrar sesión borra la sesión en los 3 roles (H-002) | P17 | Paciente: localStorage intacto | Paciente, médico y admin: localStorage `{}`; "Mis Citas" redirige al login |
| Mismo mensaje para el mismo caso (H-003) | P08, P18 | Admin: "Error al iniciar sesión…" | 401: "Credenciales inválidas" en los 3; sin servidor: "No se pudo conectar con el servidor. Intente nuevamente." |

Además, `ng build` compila sin errores nuevos (las mismas 2 advertencias NG8113 de LB-0, registradas en H-011), y el grep de claves viejas solo encuentra componentes huérfanos que no están en las rutas (H-009, H-027).

### ¿Hubo problemas imprevistos?
- **Ningún efecto no deseado en la aplicación:** las 13 pruebas fuera del objetivo dieron exactamente lo mismo que en LB-0, incluidas las que fallan (P04, P11, P13–P16).
- **Hallazgos nuevos durante las pruebas (fuera del alcance, no se corrigieron):**
  - H-028: el login de paciente no comprueba el rol; con credenciales de médico se entra a las pantallas del paciente y, como los IDs coinciden, el médico 1 ve las citas del paciente 1. Ya existía en LB-0.
  - H-027: hay otros componentes huérfanos (además de H-009) que usan las claves viejas `token` y `role`.
- **Mismo cambio en 3 archivos:** por la restricción de no unificar, el manejo de error (401 / sin conexión) se tuvo que escribir 3 veces, una en cada componente de login. Esto confirma H-008 y es la motivación de R1 DRY.
- **Herramienta de prueba:** el clic simulado de Playwright no activa algunos botones después de una navegación interna; se usó `element.click()` sobre el mismo elemento. No afecta a la aplicación.
- **Orden de la batería:** P14 se midió primero antes de P12/P13 y dio 21 / 2; se repitió en el orden del documento y dio 23 / 4, igual que en LB-0. Se dejó escrito el orden de ejecución en `PRUEBAS.md`.

### ¿Se usó el plan de back-out? ¿Por qué?
No. Todas las pruebas dieron el resultado esperado: los objetivos se cumplieron y no hubo regresiones, así que no fue necesario volver a LB-0.
