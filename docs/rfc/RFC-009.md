## Descripción del cambio

### Motivación (qué pasa hoy)
`backend/src/main/resources/application.properties` tiene escrita la contraseña real de MySQL del usuario (H-006). El archivo está versionado desde el commit inicial, así que la contraseña está en **todo el historial de Git**. El repositorio se subió a GitHub y estuvo público un tiempo con esa contraseña en el historial; el usuario ya lo pasó a privado y cambió la contraseña de MySQL. Para volver a publicarlo, la contraseña no puede estar ni en el código actual ni en ningún commit anterior.

### Por qué ocurre (causa)
La configuración de Spring se escribió con valores fijos (`spring.datasource.password=<clave>`), sin separar la configuración que cambia en cada equipo (credenciales) de la que es igual para todos (URL, driver, JPA). Cada desarrollador tiene que editar un archivo versionado con su clave, y la clave termina en el historial.

### Propósito (qué debe pasar después)
1. `application.properties` no contiene ninguna contraseña: `spring.datasource.password=${DB_PASSWORD}`, **sin valor por defecto**. Si la variable no está definida, el backend no arranca (no usa una clave escrita en el código).
2. El usuario de MySQL también sale de una variable, con `root` como valor por defecto: `spring.datasource.username=${DB_USER:root}` (el usuario no es secreto; el valor por defecto conserva el comportamiento de hoy).
3. `SETUP.md` y `README.md` explican cómo definir `DB_PASSWORD` en PowerShell (para la sesión y de forma permanente).
4. El comportamiento del sistema no cambia: la batería P01–P25 y las pruebas unitarias dan lo mismo que en LB-8.
5. La contraseña vieja se borra de **todos** los commits con `git filter-repo --replace-text` (Parte C de la tarea 15). Como eso cambia todos los hashes, se actualizan las referencias en `docs/`.

## Diseño

- Spring Boot resuelve `${DB_PASSWORD}` a partir de las variables de entorno del proceso. Sin la variable, Spring **no** se detiene en el marcador: lo deja como texto y lo usa como contraseña, y MySQL lo rechaza. Comprobado el 2026-10-21 a las 20:03:50, con la variable quitada: `Access denied for user 'root'@'localhost' (using password: YES)`, el proceso terminó con código 1 a las 20:04:00 y el puerto 8080 no respondió. Resultado: el backend no arranca y no usa ninguna clave escrita en el código, que es lo que pide la tarea.
- La prueba `CentroValdiviezoApplicationTests.contextLoads` (vieja, levanta el contexto con MySQL) también necesita la variable cuando se ejecuta `./mvnw test`.
- No se agrega un archivo `.env` ni un `application-local.properties`: la tarea pide variables de entorno y documentarlas en PowerShell.

## Alternativas evaluadas

| Alternativa | Por qué se descarta |
|---|---|
| `${DB_PASSWORD:<clave>}` con valor por defecto | Deja una clave escrita en el código; es justo lo que se quiere eliminar |
| Archivo `application-local.properties` ignorado por Git | Sigue siendo un archivo con la clave en el disco de cada uno y depende de que nadie lo agregue por error; la tarea pide variables de entorno |
| Solo cambiar el archivo actual, sin reescribir el historial | La clave seguiría en los commits LB-0 a LB-8; el repositorio no se puede publicar así |
| `git filter-branch` o BFG | `filter-branch` está desaconsejado por Git (lento, propenso a errores); BFG requiere Java aparte. `git filter-repo` es la herramienta recomendada por Git y deja la tabla de equivalencias de hashes |

- Historial completo de Git: todos los commits que contienen la clave cambian de hash; los tags LB-0 a LB-8 y ENTREGA-T2 se reescriben para apuntar a los commits equivalentes.
- `docs/`: las referencias a hashes viejos se reemplazan por los nuevos.

### Costo y tiempo estimado

### Recursos humanos
Brayan (solicitante; define la variable con la clave nueva en su equipo); Claude Code (implementación y pruebas).

### Riesgo — qué podría romperse y cómo se detectaría
- El backend no arranca si la variable no está definida en la terminal que lo lanza → se detecta al arrancar; está documentado en `SETUP.md`.
- `git filter-repo` reemplaza el texto de la clave en **todos** los archivos del historial: si la clave coincidiera con otro texto del proyecto, ese texto también se reemplazaría. Se verifica antes contando las apariciones de la clave fuera de `application.properties`.
- Los hashes citados en `docs/` dejan de existir → se reemplazan con `.git/filter-repo/commit-map` y se verifica con búsqueda.
- `git filter-repo` quita el remoto `origin` → hay que volver a configurarlo antes de subir.

## Personas afectadas
Todo el que clone el repositorio: debe definir `DB_PASSWORD` antes de arrancar el backend. Cualquier copia o clon hecho antes de la reescritura conserva la clave vieja en su historial (la clave vieja ya no sirve para MySQL porque el usuario la cambió).

## Plan de implementación
1. Respaldo completo de la carpeta (con `.git`) en `Proyecto_respaldo_antes_RFC009`.

3. El usuario define `DB_PASSWORD` (clave nueva) como variable de usuario de Windows.
4. Reiniciar el backend con la variable; batería P01–P25 y pruebas unitarias; comparar con LB-8.
5. Commit y tag `LB-9`.
6. `git filter-repo --replace-text` con la clave vieja → `***REMOVED***`; verificar 0 apariciones y los 10 tags.
7. Actualizar hashes en `docs/`; mover ENTREGA-T2 al commit final.

## Plan de back-out
Si algo sale mal antes de reescribir el historial: volver a LB-8 con el tag. Si algo sale mal **después** de `git filter-repo`: la carpeta `Proyecto_respaldo_antes_RFC009` (copia exacta, verificada con los mismos 10 tags y el mismo HEAD, `df05e56` en el historial reescrito) reemplaza a la actual.

## Evaluación post-implementación

### ¿Se cumplieron los objetivos?
- Objetivos 1 a 4: sí. `application.properties` no tiene contraseña; sin la variable el backend no arranca; `SETUP.md` y `README.md` explican cómo definirla; la batería y las unitarias dieron lo mismo que en LB-8.
- Objetivo 5 (borrar la clave del historial): ver la bitácora, entradas de la Parte C.

### ¿Hubo problemas imprevistos?
- El plan de la tarea era tomar la clave del archivo para definir `DB_PASSWORD`. No sirvió: el usuario ya había cambiado la clave de MySQL y la del archivo era la vieja (`ERROR 1045`). El usuario definió la variable con la clave nueva.
- Sin la variable, Spring no falla al resolver `${DB_PASSWORD}`: usa el texto tal cual como contraseña y falla al conectar. Se corrigió el mensaje que se había escrito en `SETUP.md`.

### ¿Se usó el plan de back-out? ¿Por qué?
No en la parte de código: los objetivos se cumplieron sin regresiones.
